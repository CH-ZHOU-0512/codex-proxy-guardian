### Codex 每次都要重连四五次才开始思考？我把这个问题做成了一个开源工具

我在 Windows 11 上使用 Codex Desktop 时，经常遇到这种情况：

浏览器和其他应用明明可以正常联网，Codex 的任务却一直重连。通常要失败四五次，它才真正开始思考。

如果你也遇到过这个现象，问题不一定是代理节点不可用。还有一种可能：**代理软件已经切换了地址或端口，但 Codex 仍在使用旧代理。**

所以我做了一个开源工具：**Codex Proxy Guardian**。

它只做一件事：

> **自动找到当前真正可用的代理，确认它能够访问 OpenAI 相关服务，再让 Codex 安全地跟上。**

项目地址：<https://github.com/CH-ZHOU-0512/codex-proxy-guardian>

### 它解决的是什么问题

Clash/Mihomo、v2rayN、sing-box 等代理程序通常会在本机监听一个 HTTP 或混合端口。

当代理程序重启、切换配置或更新后，实际监听地址和端口可能发生变化。此时可能出现这样的状态：

```text
代理软件：已经可以正常联网
Codex：   仍在使用旧地址，持续重连
```

手动处理通常需要查找当前端口、关闭 Codex、重新配置代理环境或启动参数，再打开 Codex。下一次端口变化后，还得重新做一遍。

Codex Proxy Guardian 把这套过程变成了后台守护：

```text
发现候选代理
      ↓
检查端口是否真的监听
      ↓
通过该代理执行 HTTPS 验证
      ↓
等待地址稳定，防止瞬时抖动
      ↓
更新 Codex 启动环境并进行受控重启
```

### 它和“检查端口的脚本”有什么不同

端口打开，只能说明有程序在监听，不能证明这个代理真的能让 Codex 联网。

Guardian 会继续通过候选代理访问多个 OpenAI/ChatGPT HTTPS 测试目标。只有代理通过实际验证并保持稳定，才会被选中。

状态中还会区分三层证据：

- `ValidatedProxy`：代理已经通过实际连接验证；
- `LaunchConfigured`：Codex 已经使用该代理启动；
- `TrafficObserved`：观察到 Codex 通过当前代理产生流量。

这几项状态可以帮助判断工具到底有没有生效，而不只是“脚本看起来正在运行”。

### 我最在意的几个设计点

- **实际验证**：不只判断端口是否打开，还会验证代理能否完成 HTTPS 连接；
- **避免重启循环**：带防抖、冷却、频率限制和熔断，只处理稳定变化；
- **静默运行**：安装后以当前用户身份开机自启，不需要管理员权限；
- **不破坏现有网络配置**：不修改 Windows 系统代理、WinHTTP、DNS、路由或永久环境变量；
- **能够诊断**：提供状态、日志和脱敏 Doctor 报告，出问题时可以知道卡在哪一步。

### 安装方法

从 GitHub Release 下载 ZIP，解压后在普通权限 PowerShell 中执行：

```powershell
Unblock-File .\Install.ps1
.\Install.ps1
```

安装后默认使用相对保守的 `Safe` 模式。

### 使用前需要知道

它不是代理软件，不提供代理服务或节点。电脑上需要已经存在一个可用的 HTTP/HTTPS 代理。

目前主要面向 Windows 11 + Codex Desktop，并尝试识别 Clash/Mihomo、v2rayN/Xray、sing-box 等常见程序。PAC/WPAD、纯 SOCKS，以及只有 TUN、没有 HTTP/混合端口的配置，目前不会自动支持。

项目仍处于 Alpha 阶段。不同 Windows、Codex 和代理软件版本可能存在差异，因此我更希望收集真实环境中的结果，而不是先做过度承诺。

### 如果你也遇到这个问题

可以先看 README 中的适用条件，再决定是否安装。

排查后发现，有时不是代理节点不可用，而是代理软件的监听地址或端口已经变化，Codex 还在使用旧地址。

所以我开源了 **Codex Proxy Guardian**：

- 自动发现系统代理以及 Clash/Mihomo、v2rayN、sing-box 等程序的候选端口；
- 不只检查端口，还会通过代理执行实际 HTTPS 验证；

- 静默自启，不修改 Windows 系统网络配置。

一句话说：**它不是给你提供代理，而是确保 Codex 始终跟上你当前真正可用的代理。**
